# Booking Notifications: интерфейс Ольги — 03.11.2026

По новому заданию Ольги интерфейс Booking Notifications и badge Anfragen делает
Ольга. Яна продолжает backend Chat/Notification, Nachrichten и сообщения. Код
Nachrichten и backend этим пакетом не меняется. Общие Header/keys расширены
только для Booking-уведомлений.

## Пользовательский сценарий

- У Anfragen в desktop Header, мобильной нижней навигации и гамбургер-меню
  появляется медовый badge непрочитанных Booking-событий. При нуле он скрыт,
  выше 99 показывает `99+`; экранному диктору доступно полное число.
- Сам закрытый гамбургер тоже показывает Booking badge.
- Открытие Anfragen ведёт к новой вкладке Benachrichtigungen на
  `/account/bookings/`. Meine Mieten и Eingehende Anfragen остаются доступны.
- Карточка события показывает тип, название вещи, дату/время, статус Neu,
  переход к конкретной заявке и действие Als gelesen markieren.
- Новая заявка/отмена направляет владельца в incoming, изменения статуса —
  арендатора в my-rentals. Hash указывает на `booking-<UUID>`; после загрузки
  списка нужная карточка прокручивается в видимую область и выделяется.
- Событие отмечается прочитанным только по явному действию или открытию связанной
  заявки. Открытие меню не отмечает весь список прочитанным. Ошибка не скрывает
  непрочитанное событие и показывается пользователю.
- Никаких email, браузерных push, статусов «в сети» и счётчика сообщений в этом пакете.

Счётчик означает непрочитанные события, а не общее число Booking за всё время
и не число ещё не обработанных PENDING-заявок.

## Обновление, аккаунты, ошибки

- Count/list опрашиваются раз в 15 секунд, только для вошедшего пользователя
  и без фонового polling скрытой вкладки. Дополнительно обновляются при возврате
  в окно и после изменения readAt. Это polling, а не мгновенная WebSocket-доставка.
- Query keys: `['notifications', clerkUserId, 'unread-count']` и
  `['notifications', clerkUserId, 'list']`. Прочтение инвалидирует только
  `['notifications', userId_начавшего_запрос]`.
- На 401/403/404 polling останавливается до явного обновления/повторного входа;
  404 обозначает ещё не подключённый backend, а не пустой список уведомлений.
- Некорректный DTO вызывает понятное состояние ошибки, а не ложный ноль.
- API присылает cursor; кнопка Weitere Benachrichtigungen догружает следующую
  страницу. Дубликаты между страницами не показываются дважды.

## Фактический backend-контракт

Прочитаны опубликованные Яной `d815bbf` / `6251ff5` в `origin/feat/catalog-bookings`.
Обновление 03.11: backend вошёл в main через PR #48 (fcba3a0).
Локальная ветка обновлена fast-forward, миграция 20261103110000_chat_notifications
применена к локальной PostgreSQL, Prisma Client сгенерирован. Frontend использует
реальный DTO; компоненты Nachrichten сохранены.

GET /api/me/notifications?limit=20&cursor=...:

```json
{
  "notifications": [
    {
      "id": "10000000-0000-4000-8000-000000000001",
      "type": "BOOKING_REQUEST_CREATED",
      "createdAt": "2026-11-03T10:00:00.000Z",
      "readAt": null,
      "booking": {
        "id": "20000000-0000-4000-8000-000000000001",
        "status": "PENDING",
        "item": {
          "id": "30000000-0000-4000-8000-000000000001",
          "title": "Akku-Bohrschrauber"
        }
      }
    }
  ],
  "nextCursor": null
}
```

GET /api/me/notifications/unread-count: `{ "unreadCount": 2 }`.
PATCH /api/me/notifications/read: `{ "ids": ["UUID"] }`, ответ 204.

Zod-адаптер нормализует вложенные booking.id и booking.item.title для UI.
API берёт получателя и права из серверной сессии; frontend их не подменяет.
Серверные транзакции создания событий и защита принадлежности — зона Яны.

## Передача Яне и deployment

1. Сохранить backend и frontend отдельными review-пакетами; при изменениях Header
   не перезаписать чужие добавления Nachrichten.
2. Backend Яны уже в main. После review объединить frontend Ольги с main.
3. На API применить миграцию Яны и обновить backend; затем frontend на Render.
   Новых env в UI нет. Миграция принадлежит backend-пакету Яны.
4. Двумя аккаунтами создать **новую** заявку и проверить owner badge, затем
   approve/reject/cancel/start/complete, прочтение и независимость сообщений.
   Старые заявки сами не превращаются в новые уведомления без отдельного backfill.
5. Проверить переключение аккаунтов, reload и права доступа на реальном API;
   frontend Query keys не заменяют серверные проверки.

Пакет Ольги пока локальный, commit/push/deployment в этой задаче не выполнялись.
