# Interface languages

The first release enables German (`de`), English (`en`), Ukrainian (`uk`) and Russian (`ru`).
The desktop header has a globe and a themed language button next to the account controls.
It opens a centred dialog on desktop and a bottom sheet on narrow screens, using the active site theme.
Mobile users find the same control in the menu settings. It is also available in the profile.
The current language has a check mark; Escape closes the picker and focus returns to its button.
The dialog is portalled outside the mobile drawer, so closing it keeps the drawer open.
Language names use their own spelling; flags are not used for languages.

## Implementation

- `src/i18n/config.ts`: i18next instance, supported-language registry, locale resolution and formatting.
- `src/i18n/locales/*.json`: versioned interface dictionaries. German source phrases are stable keys;
  do not change a key in one dictionary only. Named interpolation keeps user content separate.
- Components subscribe with `useTranslation()` and use `translate()` for interface strings.
  Existing form state, query caches and chat connections are retained while switching language.
- Initial priority: valid device preference, then first supported browser language, then German.
  After authentication, a saved account preference takes priority. An explicit choice while profile
  loading is pending is preserved. Unknown keys fall back to the German/source phrase.
- Guest choice is stored under `renttogether-language`. Blocked storage does not prevent switching.
- `User.preferredLocale` is nullable: old accounts retain device/browser selection until a preference
  is saved. `PATCH /api/me` accepts only enabled languages and always updates the verified caller.
  Identity synchronisation does not overwrite this preference. No extra Clerk metadata is stored.
- Account writes are serialised. Cached responses from an earlier choice/account cannot change
  the current selection. Failed saves keep the device choice and expose an explicit retry.
- Clerk's own language packs, the booking calendar, dates, currency and plural counts follow the
  selected language. Money stays in EUR; dates and numeric API formats remain unchanged.
- Categories are translated only for display. Category IDs, booking states and report-reason values
  sent to the API are unchanged. User names, locations, listing titles/descriptions and message
  bodies are original content, not machine-translated in this release.

## Add a language

1. Copy all keys from `de.json` into a new locale dictionary and translate the values.
2. Preserve every `{{placeholder}}` and supply the language's plural forms. Review long labels.
3. Add the code, native name and formatting locale to the registry and resources.
4. Add the Clerk localisation and calendar locale, and extend the profile validator.
5. For Arabic/Farsi or another RTL script, implement and verify direction, logical spacing,
   mixed-direction messages and appropriate fonts before enabling that language.
6. Run dictionary, UI, account and mobile checks. Do not show incomplete language options.

## Remaining requested languages

The requested expansion includes Turkish (`tr`), Arabic (`ar`), Polish (`pl`), Romanian (`ro`),
Albanian (`sq`), Kurdish (`ku`), Italian (`it`), Farsi (`fa`), Croatian (`hr`), Serbian (`sr`),
Bosnian (`bs`), Spanish (`es`), French (`fr`), Greek (`el`) and Bulgarian (`bg`).
These fifteen languages are not enabled yet. Add them in reviewed batches using the checklist above;
adding a name to the picker alone does not provide a translated interface.
Confirm the intended Kurdish variety and Serbian script before preparing those dictionaries.
Arabic and Farsi also need the RTL work described above. User-created listings and messages need a
separate translation feature if translation of that content is required.

## Verification and rollout

`npm run test:translations` checks dictionary parity, interpolation, plurals and locale resolution.
`npm run test:i18n` uses an isolated local identity/API fixture for selection, persistence, account
changes, failed saves, category filter values, draft preservation and responsive navigation.
Its Clerk alias is used only by `tests/i18n/vite.config.ts`; production auth is unchanged.
Database integration tests verify persistence across fresh connections and identity sync, account
isolation and rejection of invalid/anonymous writes. Real Clerk sessions are checked separately by
`npm run test:auth` using development keys and local PostgreSQL.

Deploy the API with migration `20261121110000_user_preferred_locale` first, then the frontend.
The nullable column is additive. A frontend rollback remains compatible with the migrated database.
Automatic translation of listings and messages and the remaining requested languages are later phases.
