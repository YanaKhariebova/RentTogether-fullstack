# Передача объявлений в интеграцию Booking

Подготовлено 30 октября 2026 года. Ответственная за объявления — Ольга,
за Booking — Яна. Это план будущей проверки; непроведённые шаги не считаются успешными.

## Что уже предоставляет часть объявлений

- Item.id, ownerId, categoryId — UUID; в JSON это строки.
- pricePerDay — Decimal(8,2) в БД и строка с двумя знаками в JSON.
- Item содержит createdAt; фотографии доступны через images[].url в порядке order.
- Создание сохраняет черновик. Публикация — отдельное действие, требует фото.
- DELETE /api/items/:id снимает вещь с публикации и сохраняет строку Item и фотографии.
- Изменение цены вещи не должно менять снимок цены в уже созданной заявке.
- Изменения объявления/фото используют блокировку строки Item внутри транзакции.

Для Booking разрешено добавить обратные relations в Item и User новой миграцией.
Существующие миграции не переписываем. Арендатор берётся из текущего пользователя
на сервере; клиент не назначает чужого renter и не рассчитывает доверенную цену.

## Подготовка совместной проверки

1. Объединить Booking через review, получить актуальный main в рабочую ветку.
   Перед merge убедиться, что git status чистый.
2. Установить зависимости согласно изменениям package-lock и применить новые
   миграции командой npm --prefix server run db:deploy при запущенной PostgreSQL.
3. Проверить локальные env по [инструкции запуска](foundation-setup.md).
   Адрес браузера должен совпадать с CLIENT_URL; после изменения env перезапустить сервисы.
4. Использовать два отдельных профиля браузера: A — владелец, B — арендатор.
   Для проверки одновременного подтверждения добавить третьего участника C.
5. Через форму создать отдельное объявление «Demo Beamer», Berlin, Elektronik,
   15,50 EUR/день. Добавить два разрешённых к использованию фото и опубликовать.
   Не изменять чужие объявления и не очищать общую БД.

## Проверки после реализации Booking

Даты ниже — пример для будущей демонстрации: 9–12 ноября 2026 года.
При более позднем запуске выбрать другие будущие даты. День возврата не оплачивается:
три дня по 15,50 EUR дают 46,50 EUR.

| Шаг | Действие                                                      | Ожидаемый результат                                                        |
| --- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 1   | B находит Demo Beamer в каталоге и открывает карточку         | Данные и порядок фото совпадают с кабинетом A                              |
| 2   | B отправляет заявку на три дня                                | PENDING; backend сохраняет pricePerDaySnapshot="15.50", totalPrice="46.50" |
| 3   | A открывает входящие, B — свои аренды; оба обновляют страницы | Одна и та же заявка сохраняется после reload                               |
| 4   | A меняет цену вещи на 20,00 EUR                               | Старая заявка сохраняет 15,50 и 46,50; новая считает сумму по новой цене   |
| 5   | A подтверждает заявку                                         | APPROVED, даты заняты для пересекающихся подтверждений                     |
| 6   | A переводит заявку в ACTIVE, затем COMPLETED                  | Разрешённые переходы видны обоим участникам после reload                   |
| 7   | A снимает вещь с публикации с подтверждением                  | В каталоге вещь исчезает; существующая заявка и её снимок цены сохраняются |

Дополнительные проверки прав и ошибок:

- [ ] A не может забронировать собственную вещь.
- [ ] Неопубликованная вещь недоступна для создания новой заявки через прямой API-запрос.
- [ ] Прошедшая дата получения, одинаковые даты и возврат раньше получения отклоняются.
- [ ] B отменяет только собственную PENDING заявку; владелец отклоняет PENDING.
- [ ] Чужой пользователь не может читать приватную заявку или менять её статус.
- [ ] При пересечении с APPROVED/ACTIVE подтверждение возвращает 409 BOOKING_DATES_UNAVAILABLE.
- [ ] Два одновременных подтверждения пересекающихся заявок не создают две активные брони.
- [ ] Диапазоны [9,12) и [12,14) не пересекаются: возврат и следующее получение в один день разрешены.
- [ ] Сбой API показывает ошибку и возможность повтора, без ложного сообщения об успешной отправке.
- [ ] Основной сценарий доступен с клавиатуры и на узком экране.

Проверки пересечений и одновременных подтверждений должны иметь автоматические
API/DB-тесты в части Booking. Этот документ их не заменяет.

## Что записать по результатам

Дата, commit, проверявший, выбранные будущие даты, статус каждого шага и найденные
ошибки. Секреты, JWT и пароли в отчёт не включать. После проверки скрыть только
созданное для неё объявление; заявки сохранять до завершения командного review.
