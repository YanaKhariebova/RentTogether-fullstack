# Внутренние уведомления — требования к первой версии

Актуализация: 03.11.2026. Ответственная за реализацию — Яна; Ольга согласовала
объём и правила в командной переписке. Это контракт/план, не утверждение о наличии
модели или готового API. Итоговые enum-имена и ограничения ниже подтверждены Ольгой 03.11; можно начинать миграцию после обновления ветки от main.

## Объём и события

Только уведомления внутри сайта, без email, push и статусов «в сети».

- Создание заявки арендатором → уведомление владельцу.
- Подтверждение, отклонение, начало и завершение аренды владельцем → арендатору.
- Отмена заявки арендатором → владельцу.

Событие и уведомление записываются одной транзакцией. Откат не оставляет уведомления;
повторный запрос одного перехода не создаёт дубликат.

## Черновик модели

- id — UUID.
- userId — получатель; определяется сервером.
- type — enum события Booking.
- bookingId — связанная заявка.
- createdAt.
- readAt — nullable.

Текст и ссылка формируются frontend из type и bookingId. Скрытие вещи не должно
лишать участников доступа к их существующей заявке и связанной истории.

## API

- GET /api/me/notifications — только свои уведомления, с пагинацией и стабильной
  сортировкой createdAt DESC, затем id DESC.
- GET /api/me/notifications/unread-count — свой счётчик.
- PATCH /api/me/notifications/read — тело `{ ids: [...] }`, только свои входящие
  уведомления; повторный вызов не изменяет первоначальный readAt.

Все маршруты защищены auth. Открытие меню само по себе не отмечает весь список
прочитанным: действие относится к конкретному уведомлению при переходе к заявке
или явном выборе пользователя. Данные Query и счётчики разделяются по пользователю.
Обновление — после действий и периодическим опросом; мгновенная доставка не обещана.

## UI и связь с чатом

Яна ведёт Header/mobile navigation и интегрирует Benachrichtigungen/badge:
при 0 badge скрыт, при значении больше 99 — `99+`. Точное соседство с Nachrichten
согласовать перед изменением навигации.

Для чата впоследствии можно использовать тот же раздел уведомлений, но readAt
уведомления и readAt сообщения — разные состояния. Прочтение уведомления
не отмечает автоматически ещё не показанные сообщения чата.

PWA push в этот контракт не входит. [Текущая ответственность](team-status.md),
[согласованный Chat](chat-contract.md).

## Уточнение перед миграцией — 03.11.2026

Со стороны Ольги подтверждено: **можно начинать миграцию**. Conversation/Message
сохраняют поля из chat-contract.md; отправка разрешена только при PENDING,
APPROVED и ACTIVE. Проверки участников диалога и прочтение до lastReadMessageId
остаются частью контракта.

Принят NotificationType:

- BOOKING_REQUEST_CREATED
- BOOKING_APPROVED
- BOOKING_REJECTED
- BOOKING_CANCELLED
- BOOKING_ACTIVE
- BOOKING_COMPLETED

Для Notification согласованы @@unique([bookingId, userId, type]) и
@@index([userId, createdAt, id]). Уникальность подходит для текущих
однонаправленных переходов Booking без повторного входа в прежний статус.
Списки используют cursor-пагинацию. Эта запись разрешает начать работу,
но не означает, что локальная Prisma-схема уже изменена.
