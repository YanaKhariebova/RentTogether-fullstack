# Фотографии: адаптер хранилища — 29.10.2026

29.10 команда выбрала Cloudinary. Его адаптер реализован, настоящий аккаунт
и браузерный сценарий проверены 29.10.2026. Настройка описана в [инструкции](cloudinary-setup.md). Для разработки
сохраняется локальный режим с файлами в `server/uploads/`.
Бинарные данные не попадают в PostgreSQL и Git. Фронтенду нужен только `image.url`.

## Структура

- `server/src/modules/items/storage/ImageStorage.ts`: общий контракт.
- `storage/localImageStorage.ts`: локальные файлы, UUID-имена, защита пути.
- `imageValidation.ts`: серверная проверка и нормализация через sharp.
- `service.ts`: права, количество фото, транзакции и компенсация upload.
- `imageCleanup.ts`: повторное удаление объектов после сбоя.
- `server/src/index.ts`: выбор и подключение адаптера, повтор очистки каждые 30 секунд.

```ts
interface ImageStorage {
  upload(image: {
    content: Buffer;
    contentType: 'image/jpeg' | 'image/png' | 'image/webp';
  }): Promise<{ key: string }>;
  delete(key: string): Promise<void>;
  getPublicUrl(key: string): string;
}
```

Ключ генерирует адаптер; клиент его не передаёт. Upload должен вернуть ключ только
после успешной записи и убирать частично записанный объект при ошибке. Delete
идемпотентный: отсутствие объекта считается успехом. URL должен быть стабильным,
публично доступным HTTP(S) адресом, а не короткоживущей подписанной ссылкой.
API возвращает только id/url/order; storageKey остаётся на сервере.

## Локальный запуск

Из корня проекта, при уже настроенных Clerk и DATABASE_URL:

```sh
npm --prefix server ci
npm --prefix server run db:deploy
npm --prefix server run dev
```

База должна быть запущена, например через `npm --prefix server run db:local`
в отдельном терминале. Если локальная БД уже работает, повторно запускать её не нужно.
Новая миграция добавляет только служебную таблицу ImageCleanup; Item/ItemImage
и существующие данные не меняются.

Дополнительные параметры `server/.env` (при стандартном порте можно не добавлять):

```dotenv
IMAGE_STORAGE=local
IMAGE_PUBLIC_BASE_URL=http://localhost:3000/uploads/
```

URL берётся из серверной конфигурации, а не из HTTP Host клиента. Папка uploads
определяется относительно файла модуля и не зависит от текущей директории терминала.
Файлы раздаются по `/uploads/<key>`, с `X-Content-Type-Options: nosniff`.
При NODE_ENV=production требуется IMAGE_STORAGE=cloudinary и полная конфигурация
аккаунта. Выбор и маршрутизация ключей находятся в storage/configureImageStorage.ts.

## API и совместимость с веткой Яны

- POST `/api/items/:id/images`: один бинарный файл, 201 `{ image }`.
- DELETE `/api/items/:id/images/:imageId`: 204 без тела.
- PUT `/api/items/:id/images/order`: полный `{ imageIds }`, 204, как в прототипе Яны.
- PATCH того же URL: тот же порядок, 200 `{ item }`.

Подробности и ошибки — в [контракте](items-api.md). Типы/проверка содержимого,
лимит 8 фото и права не зависят от провайдера. Все изменения фото и публикация
берут одинаковый FOR UPDATE lock на Item.

Ветка Яны уже содержит свой imageStorage.ts, маршруты и useOwnerItems. При интеграции
оставить одну реализацию маршрутов и подключить её к ImageStorage из этого пакета;
не возвращать старый обмен позиций напрямую, он нарушает UNIQUE(itemId, order).
Последовательность frontend-запросов из прототипа Яны адаптирована в useOwnerItems
с Query, асинхронной формой и возобновляемой save-сессией. Чужая ветка целиком
не объединялась: при её дальнейшем merge сохранить эту реализацию owner-кабинета.

## Удаление и сбои

При удалении строка фото и задание ImageCleanup меняются в одной транзакции.
После commit сервер сразу пытается удалить объект; при отказе задание остаётся
в PostgreSQL и повторяется в фоне и после перезапуска. Поэтому 204 означает,
что фото убрано из объявления; сам объект при сбое может удалиться позже.
Последнее фото опубликованной вещи защищено от удаления.

Если upload удался, а регистрация в БД откатилась, объект удаляется компенсирующим
вызовом; при отказе провайдера тоже создаётся задание ImageCleanup. Если одновременно
недоступны и БД, и провайдер, потребуется сверка объектов: ключ записывается в
серверный журнал. Аварийное завершение процесса между upload и commit также требует
периодической сверки неиспользуемых объектов перед production. Общей транзакции
между PostgreSQL и внешним хранилищем нет.

Перед сменой провайдера обработать оставшуюся очередь и перенести существующие
файлы/URL либо сохранить доступ к старому хранилищу. Подмена адаптера сама по себе
не переносит уже записанные файлы.

## Проверки

```sh
npm --prefix server test
npm --prefix server run db:check
npm --prefix server run build
npm --prefix server run lint
```

Тесты используют временную папку и изолированную PostgreSQL. Проверяются реальные
байты изображений, подмена MIME, размеры, права, сохранение/раздача/удаление,
конкурентный лимит количества, очередь удаления и альтернативный тестовый провайдер.
Сквозной сценарий с настоящими Development Clerk-пользователями проверен в Chrome
через tests/auth/items.spec.ts. Настоящий Cloudinary upload, public URL и delete проверены 29.10.2026, включая браузерный сценарий.

Параметры декодирования и удаления метаданных сверены с официальной документацией
[sharp constructor](https://sharp.pixelplumbing.com/api-constructor/) и
[sharp output](https://sharp.pixelplumbing.com/api-output/).
